## 主な技術的知見

1. 🔴 **`--ignore-unreachable` を使わない。** composer には取得失敗を無視するフラグが実在するが、付けると **「advisory が無い」と「確かめられなかった」が同じ exit 0 に潰れる**。監査を独立ステップに保っている理由（#792 = 走ったかどうかがログで判ること）を、それ自身で無効化する。**上流障害も赤のまま落とし、理由だけを読めるようにする**のが本 repo の方針。

2. ⚠️ **`composer audit` の既定の監査対象は `composer.lock` ではなく `vendor/`（installed）。** CI は直前に `composer install` を通すので差は無いが、**手元では嘘をつく**。この日それを実際に踏みかけた — 素の `composer audit` が smarty の CVE 2件を返したが、`composer.lock` は **v5.8.4**、`vendor/composer/installed.json` は **v5.8.0（2026-05-26）**で、`composer audit --locked` は `exit 0`（clean）。⇒ **手元で叩くときは `--locked` を付ける。** 休眠リポほど vendor が古く、解消済みの CVE が再燃して見える。

3. ⚠️ **リトライを過大評価しない。** `0/60/300` 秒を入れたが、当日の障害 **26分49秒**は救えない。効くのは分類のほう。**「対策を入れた」と「その対策が当日の事象を防げた」は別**なので、コメントに実測値ごと残した。

4. 🔴 **リハーサル口は、本番経路の手前で止まりやすい。** #795 の `simulate_failure` は Setup PHP より前で `exit 1` するため audit ステップに到達せず、**分類も outputs も動かない**。同じ罠を `simulate_audit_exit` でも踏みかけた（`notify-failure` の `if` に阻まれる）。⇒ **口を足すときは「その口が本番と同じ経路を通るか」を経路の端まで辿る。**

5. 🔴 **終了コードを測るときパイプを挟まない。** `cmd | tail; echo $?` は `tail` の値を拾う。`cmd > file 2>&1; echo $?` にして出力は後から読む（`| head` の SIGPIPE も同族）。同日 hub がこれで `exit=0` を得て「区別できていない」と誤判定しかけた。**A と B が両方 0 で並んで初めて矛盾に気づいた**もので、1本だけ測っていれば通っていた。

6. 🔴 **スタブで通ったことを実 CI の証拠に読み替えない。** ジョブ間の伝播はスタブでは測れないので「未検証」と明示して PR を出し、リハーサルで実測に変えた。

7. ⚠️ **squash マージのリポでは `git merge-base --is-ancestor` / `git branch -d` が必ず「未マージ」と言う。** この日削除した3本とも false だった。**これを未マージの根拠にすると幻の仕掛かりが生まれる。** 正しくは `git diff --name-only origin/main...<枝>` で枝が触ったファイルを列挙し、1つずつ main と内容比較する。差分が出たら現物を読む（実例: `ci/notify-failure-2026-08-22` に差分4行が出たが、すべて #797 が置き換えた旧版だった）。

8. ⚠️ **`gh pr view --json mergedBy` は打鍵者を示さない。** `gh` がリポジトリ所有者のトークンで動くため、**トークンの持ち主**が出るだけ。#795 / #797 は施主承認のうえ hub が打鍵した。記録には「誰が承認し、誰が打鍵したか」を分けて書く。

9. ℹ️ **`workflow_dispatch` の inputs は指定した `--ref` の定義で解決される。** デフォルトブランチ側で検証されるのではないかと疑ったが、**マージ前の枝でも新しい input を渡せた**（否定された）。
